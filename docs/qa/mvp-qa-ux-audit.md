Дата аудита: 11 сентября 2026 года.

## Fixed issues

### ISSUE-001

Severity: Critical

Problem: модератор мог произвольно установить любой статус задачи, включая `ACCEPTED` или `CLOSED`, не изменяя связанную запись назначения.

How it affected the user: задача и назначение расходились по статусам; основной цикл мог стать непроходимым без ручного изменения БД.

Root cause: admin API принимал весь список Task statuses и обновлял только таблицу `tasks`.

Fix: admin-переходы ограничены безопасными состояниями модерации. Рабочие статусы меняются только действиями заказчика и исполнителя. В UI свободный status-select заменён статусом и действиями «Опубликовать», «Скрыть», «Показать».

Verification: негативный API-тест запрещает модератору перевести назначенную задачу в `ACCEPTED`; отдельно проверены публикация черновика и скрытие/возврат публикации.

### ISSUE-002

Severity: High

Problem: API принимал дедлайн `1111-01-01`, прошлую дату, несуществующую дату и произвольно далёкий год.

How it affected the user: в каталоге появлялись заведомо невыполнимые задачи и некорректные сроки.

Root cause: сервер проверял только формат строки `YYYY-MM-DD`.

Fix: добавлена календарная проверка и доменный диапазон: срок новой задачи — от завтра до двух лет вперёд. Те же границы показаны через `min`, `max` и пояснение в форме.

Verification: тесты отклоняют прошлую дату, `1111-01-01`, `2026-02-31` и дату дальше 730 дней.

### ISSUE-003

Severity: High

Problem: бюджет, цена отклика и ставка принимали `0` и практически неограниченные значения.

How it affected the user: бессмысленные суммы попадали в карточки и назначения.

Root cause: общий numeric validator проверял только целое неотрицательное число.

Fix: введены осознанные границы MVP: проект/отклик — 1 000–100 000 000 ₽; необязательная ставка — 100–100 000 ₽/час. Используется `Number.isSafeInteger`; клиентские поля имеют такие же `min/max`.

Verification: API-тесты отклоняют `0`, `1e100` и число выше максимума.

### ISSUE-004

Severity: High

Problem: после отправки отклика исполнитель продолжал видеть кнопку «Откликнуться»; после выбора другого кандидата ссылка из его списка могла вести в 404.

How it affected the user: действие было заведомо невыполнимым, а история собственного отклика превращалась в тупик.

Root cause: карточка задачи не возвращала текущий отклик, а право read-only просмотра после назначения было только у выбранного исполнителя.

Fix: API возвращает `myApplication`; любой откликнувшийся сохраняет read-only доступ к карточке. UI показывает фактический статус и следующий путь вместо повторной кнопки.

Verification: тест создаёт двух кандидатов, выбирает одного, проверяет статус `REJECTED`, доступ второго к карточке и запрет доступа к рабочей странице.

### ISSUE-005

Severity: High

Problem: при ширине до 960 px основная навигация полностью скрывалась без замены.

How it affected the user: на планшете и телефоне нельзя было напрямую открыть каталог, личные задачи, входящие отклики или модерацию.

Root cause: media query задавал `.nav { display: none; }`, а mobile menu отсутствовало.

Fix: добавлено клавиатурно доступное mobile menu с `aria-expanded`, закрытием по Escape и полноразмерными пунктами.

Verification: проверены DOM-состояния и CSS breakpoints 960/680 px; все ключевые ссылки присутствуют в одном navigation landmark.

### ISSUE-006

Severity: High

Problem: сохранённый черновик можно было только опубликовать; исправить его в UI было невозможно, хотя API редактирования существовал.

How it affected the user: ошибка или неполное описание в черновике требовали создавать новую задачу.

Root cause: отсутствовал маршрут и предзаполненная форма редактирования.

Fix: добавлен `/tasks/:id/edit`, переиспользующий форму создания. Доступ ограничен владельцем/модератором и состояниями до назначения. Черновик можно сохранить или опубликовать после редактирования.

Verification: маршрут включён в SPA smoke-test; сервер повторно проверяет владельца и допустимый статус.

### ISSUE-007

Severity: High

Problem: исполнитель мог предложить срок в прошлом или позже дедлайна задачи.

How it affected the user: заказчик мог принять внутренне противоречивое предложение.

Root cause: proposed deadline проверялся только регулярным выражением.

Fix: срок отклика ограничен диапазоном «сегодня — дедлайн задачи» на клиенте и сервере.

Verification: тесты отклоняют прошлую дату и дату позже срока задачи.

### ISSUE-008

Severity: High

Problem: поле ссылки результата принимало произвольную схему, включая `javascript:`.

How it affected the user: сохранялась небезопасная и неработоспособная ссылка. CSP снижал риск выполнения, но данные оставались некорректными.

Root cause: сервер валидировал ссылку как обычный текст.

Fix: необязательная ссылка допускает только полные `http://` и `https://` URL; форма показывает формат.

Verification: негативный тест отклоняет `javascript:alert(1)`.

### ISSUE-009

Severity: Medium

Problem: карточка задачи, публичный профиль, рабочая страница и входящие отклики не имели явного пути на логичный верхний уровень.

How it affected the user: особенно на mobile было непонятно, как вернуться к списку или рабочему разделу.

Root cause: навигация полагалась только на desktop header и системную кнопку браузера.

Fix: добавлены контекстные переходы «Все задачи», «К задачам», «Мои задачи», а на рабочей странице — ссылка на исходную карточку.

Verification: все detail-маршруты просмотрены по карте навигации; fallback всегда является явной ссылкой.

### ISSUE-010

Severity: Medium

Problem: после отклика пользователь попадал на вкладку созданных задач; исполнитель после обычного/демо-входа также попадал в малополезный раздел.

How it affected the user: успешное действие выглядело потерянным, а стартовый экран исполнителя часто был пустым.

Root cause: редиректы не учитывали контекст и основную роль.

Fix: после отклика открывается `/my-tasks?tab=applied`; активная вкладка хранится в URL. Исполнитель после входа попадает в каталог, заказчик — в свои задачи, а `next` сохраняется через авторизацию.

Verification: логика маршрутов проверена синтаксически и в SPA route smoke-test.

### ISSUE-011

Severity: Medium

Problem: недоступное действие объяснялось одной фразой «ожидается от другой стороны» независимо от статуса.

How it affected the user: заказчик и исполнитель не понимали, кто и что должен сделать дальше.

Root cause: один fallback-текст для всей статусной машины.

Fix: для `ASSIGNED`, `IN_PROGRESS`, `SUBMITTED`, `ACCEPTED`, `CLOSED` добавлены разные сообщения с конкретной ответственной стороной и следующим событием.

Verification: все пять состояний сопоставлены с ролью viewer; E2E проходит каждое состояние.

### ISSUE-012

Severity: Medium

Problem: percentage matching выглядел как «магическое» число и перечислял только общий текст о совпадении.

How it affected the user: заказчик не видел пробелы профиля и мог переоценить score.

Root cause: matcher возвращал только `matchedSkills` и собранную строку.

Fix: matcher возвращает совпавшие и отсутствующие навыки, количество совпадений и отдельное объяснение случая без skills. UI подчёркивает, что это подсказка, а не автоматическое решение.

Verification: unit-тесты проверяют alias `CV → Computer Vision`, 100% score и пустой список навыков.

### ISSUE-013

Severity: Medium

Problem: просроченная опубликованная задача считалась активной и визуально предлагала отклик.

How it affected the user: попытка завершалась непонятной ошибкой диапазона даты.

Root cause: каталог и CTA учитывали только статус, но не deadline.

Fix: просроченные задачи исключаются из каталога и публичной статистики; API отклика возвращает явную ошибку, а прямая карточка показывает объяснение вместо CTA.

Verification: каталог использует доменную границу текущего дня, а application API содержит отдельную проверку истёкшего срока.

### ISSUE-014

Severity: Medium

Problem: при запросе кнопки только становились полупрозрачными; ошибки формы показывались временным toast.

How it affected the user: на медленной операции было неясно, отправляется ли форма; сообщение об ошибке легко пропустить.

Root cause: не было общего loading label и постоянного form error.

Fix: submit/action buttons показывают «Подождите…», блокируют повторное нажатие и восстанавливаются при ошибке. Серверная ошибка добавляется в форму как `role=alert` и получает focus.

Verification: все submit handlers используют общий `busy`, все action handlers — `actionBusy/resetAction`.

### ISSUE-015

Severity: Medium

Problem: пустые вкладки «Мои задачи» объясняли состояние, но не предлагали прямое действие.

How it affected the user: новичок понимал причину пустоты, но вынужден был самостоятельно искать следующий экран.

Root cause: helper пустого состояния не получал CTA для вкладок.

Fix: добавлены «Создать задачу», «Найти задачу» и «Перейти в каталог» по контексту вкладки.

Verification: проверены три пустых panel state в `/my-tasks`.

### ISSUE-016

Severity: Medium

Problem: заказчик мог после получения отклика сократить дедлайн задачи до даты раньше предложенного кандидатом срока.

How it affected the user: сохранённое предложение становилось противоречивым после редактирования задачи.

Root cause: update Task не учитывал активные Applications.

Fix: сервер запрещает дедлайн раньше максимального срока среди активных откликов и сообщает конкретную конфликтующую дату.

Verification: добавлен негативный тест редактирования после отклика.

### ISSUE-017

Severity: Low

Problem: выход обозначался символом внешней ссылки `↗`.

How it affected the user: назначение кнопки было неочевидно без tooltip.

Root cause: слишком абстрактная icon-only кнопка.

Fix: кнопка подписана «Выйти» и имеет полное accessible name.

Verification: header проверен для гостя и авторизованного пользователя.

### ISSUE-018

Severity: Low

Problem: modal доработки не имел dialog semantics; focus не переносился в dialog и не возвращался; tabs не сообщали selected state.

How it affected the user: клавиатурная навигация и работа screen reader были менее предсказуемы.

Root cause: базовые ARIA/focus states были реализованы частично.

Fix: добавлены `role=dialog`, `aria-modal`, связанный title, initial/return focus, Escape; tabs получили `role`, `aria-selected`, `aria-controls`, panels — `role=tabpanel`. Добавлен явный `:focus-visible`.

Verification: статически проверены атрибуты и клавиатурные handlers.

### ISSUE-019

Severity: Low

Problem: длинные названия/неразрывные строки и ряд вкладок могли выходить за контейнер на узком экране.

How it affected the user: появлялся нежелательный горизонтальный overflow или обрезание текста.

Root cause: отсутствовали общие правила переноса, tabs не имели локального overflow.

Fix: добавлен `overflow-wrap: anywhere`; tabs имеют контролируемый horizontal scroll и не ломают страницу; таблицы остаются в собственном scroll-container.

Verification: проверены breakpoints 960 и 680 px и контейнеры task/profile/admin.

## Remaining limitations

- Встроенный браузер в текущей среде вернул отсутствие доступных browser backends. Поэтому не выполнены screenshot-based проверки реального layout и ручной keyboard walkthrough; вместо них выполнены HTTP smoke-test, анализ DOM/CSS и API E2E.
- Подтверждения критичных действий используют нативный `confirm`. Для MVP это понятно и надёжно, но визуально зависит от браузера.
- Email/Telegram-уведомления, чат и платежи остаются вне согласованного MVP scope. Пользователь должен самостоятельно возвращаться на платформу для проверки нового статуса.
- Модерация намеренно операционная: нет журнала решений отдельного уровня, массовых действий и автоматического trust & safety.

## Tested user flows

### Незарегистрированный пользователь

- Главная → каталог → карточка задачи.
- Переход к регистрации/входу и возврат через `next`.
- Прямой переход на защищённые и несуществующие маршруты.
- Человекочитаемый 404 для отсутствующей задачи.

### Заказчик

- Регистрация и duplicate-email error.
- Создание черновика, редактирование и публикация.
- Валидация обязательных полей, дат, skills и бюджета.
- Просмотр откликов, matching и выбор ровно одного исполнителя.
- Запрет повторного назначения и действий исполнителя.
- Просмотр результата, принятие, отзыв и закрытие.

### Исполнитель

- Регистрация, профиль и валидация ставки.
- Каталог, поиск, фильтры и объяснимый matching.
- Валидация цены/срока отклика, создание и запрет дубля.
- Просмотр собственного SUBMITTED/REJECTED отклика.
- Запрет доступа отклонённого кандидата к рабочей странице.
- Старт, запрет повторного старта, отправка результата и URL validation.
- Получение статуса и двусторонний отзыв.

### Модератор

- Доступ к воронке, пользователям и задачам.
- Публикация черновика, скрытие и возврат видимости.
- Запрет произвольного изменения lifecycle-статуса.
- Запрет admin API для обычного пользователя.

### Регрессия

- Полный Task → Application → Assignment → Work → Result → Acceptance → Reviews → Closed.
- История статусов и обязательные analytics events.
- Все клиентские маршруты отдаются через SPA.
- `npm run check` и `npm test` проходят.
